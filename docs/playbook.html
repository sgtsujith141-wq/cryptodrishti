Project playbook · read before you present

CryptoDrishti, end to end

Everything about this project in one place: what it does, how to drive it, what every sensor looks for, how the scoring maths works, and how the code is put together — file by file. Written so you can answer any question about it without having written it.

01

What this actually is

In one sentence: it is a virus scanner, except it hunts cryptography instead of malware, and then tells you what to replace each thing with.

You point it at a codebase or a directory. It reads the source, the compiled binaries, the certificates, the dependency manifests and the config files, and it finds every piece of cryptography in there. Then it works out which of those will be broken by a quantum computer, ranks them by how much that matters, recommends a post-quantum replacement for each, and exports the whole thing as a CBOM — a Cryptography Bill of Materials, in the international standard format.

Why anyone wants this

Quantum computers will break RSA and elliptic-curve cryptography, which is what secures essentially all internet traffic. NIST published the replacements in 2024, so the mathematics is solved. Almost nobody has migrated — because migration requires knowing what cryptography you have, and no organisation does. India's national roadmap requires critical-infrastructure operators to produce exactly this inventory by December 2027. This tool produces it.

Everything runs locally. There is no cloud service, no API key and no outbound network call anywhere in the product — which is the point, because the organisations that most need this run classified networks that a cloud tool cannot reach.

Running it — every command

The one you use before presenting

# Start the server AND pre-run a scan so the console opens already populated.
# Do this WITH network, before you walk in — then the cable-pull is real.
./.venv/bin/python run.py --seed \
    --seed-path demo/targets/openssl \
    --seed-endpoints www.google.com

Then open http://127.0.0.1:8000.

Never skip this

./.venv/bin/python run.py --preflight — it tests all fifteen things the demo depends on and prints ALL CLEAR or exactly what is broken. Run it before you walk in and again on the morning. If something is wrong, --demo-reset rebuilds the exact demo state in one command.

04

Choosing what to scan

This matters more than it sounds, because the demo is only as convincing as what is on the screen. A good target has three properties: a name the judges recognise, enough findings to look serious but few enough to stay readable, and at least one finding dramatic enough to click into.

Use this one

demo/targets/openssl. Everyone in the room knows what OpenSSL is, the problem statement itself names OpenSSL as an acceptable dataset, and it yields 77 assets with a clean severity spread including MD5, DES, RC4, SHA-1 and 260 RSA-2048 certificates. It also contains six post-quantum certificates, so you can show that the tool measures migration progress, not only debt.

TargetAssetsCharacter
demo/targets/openssl77The demo target. C, huge crypto surface, recognisable name, great spread.
demo/targets/paramiko~17Python SSH library. Small and fast; good for showing the AST analysis specifically.
demo/targets/django~28Big Python web framework. Slower scan, fewer asymmetric findings.
demo/targets/shiro~77Java security framework. Useful to show wrapper-class detection.
/usr/local/lib9The binary beat. Real compiled libraries, no source at all.

If you want to add a new target

  1. Clone it shallow: git clone --depth 1 <url> demo/targets/<name>. It appears in the Preset dropdown automatically — the dropdown is built by listing that directory.
  2. Scan it from the command line first: python -m app.cli scan demo/targets/<name> --top 20. Look at the output before you trust it on stage.
  3. Reject it if it produces fewer than about fifteen assets, or if the top findings are all in test fixtures — both look weak on a projector.
Do not scan on stage without having scanned it first

Every target should be scanned in rehearsal. A repository you have never scanned might produce four findings, or take ninety seconds, and you will not know until it is on the projector.

05

What it looks for

The tool knows 52 algorithms. Every finding resolves to one of them, and that entry decides how the finding is classified, scored and remediated. The registry lives in app/knowledge/algorithms.py.

Everything is sorted into five classes. This is the single most important idea in the whole tool, and it is what makes it more than a grep:

ClassCountMeaningExamples
Broken by Shor20 A quantum computer recovers the private key outright. Key size does not help. Must be replaced. RSA, ECDSA, ECDH, DH, DSA, Ed25519
Weakened by Grover12 Effective strength halves. Fixed by a bigger parameter set, not a different algorithm. AES-128, SHA-1, MD5, 3DES, RC4
Quantum-safe18 No known quantum attack beyond generic search. The migration targets. ML-KEM, ML-DSA, SLH-DSA, AES-256, SHA-384
Hybrid1 Classical and post-quantum combined; secure if either half holds. The correct default for TLS today. X25519MLKEM768
Unresolved1 Detected as cryptographic but not pinned to an algorithm. Reported, never guessed. unknown

Each registry entry carries more than a class — classical strength in bits, NIST quantum security level, the OID, the standard it comes from, key and signature sizes in bytes, and the years it becomes deprecated and disallowed under NIST IR 8547. Those fields are what let the tool reason rather than merely label.

Beyond quantum: things that are just broken

The tool also flags defects that have nothing to do with quantum computing, because an inventory that ignored them would be strange:

  • Hardcoded private keys and secrets in source — compromised the moment the repository is cloned.
  • ECB mode — leaks plaintext structure regardless of key size.
  • Non-cryptographic random number generators — Math.random, java.util.Random, Python's random. A predictable generator defeats every algorithm above it.
  • Expired and weakly-signed certificates — SHA-1 or MD5 signatures, RSA below 2048 bits.
  • Deprecated protocol versions — TLS 1.0 and 1.1, removed by RFC 8996.
06

The six sensors

Each sensor is an independent module in app/scanners/. They all return the same shape — a list of Finding objects — so the rest of the pipeline does not care where a finding came from. One sensor failing never takes the scan down; a malformed binary or an unreachable host is a normal condition in a real estate.

source.py · 362 lines

1 · Source code

Two passes. For Python it parses the real syntax tree, so a match cannot come from a comment or a string, and key_size=2048 resolves to an actual value. For the other nine languages it applies 49 pattern rules, skipping comment lines first. Where both passes see the same line, the syntax-tree result wins.

Finds: algorithm, mode and padding at each call site — Cipher.getInstance("AES/ECB/PKCS5Padding") yields AES and ECB and PKCS#5, not merely "crypto happened here".

deps.py · 189 lines

2 · Dependencies

Reads requirements.txt, package.json, pom.xml, build.gradle, go.mod, Cargo.toml and friends, then maps each library to what cryptography it can perform and whether that version has post-quantum support.

Finds: "BouncyCastle 1.68 — below 1.79, so no ML-KEM; here is the upgrade path." Most applications never call crypto directly, so without this you miss most of the real surface.

binary.py · 278 lines

3 · Binaries and firmware

The differentiator. Three techniques in descending confidence. Symbol tables: for ELF we parse the section headers and read .dynstr directly. Constants: AES S-boxes and SHA-256 round constants sit verbatim in read-only data and survive stripping, because they are data rather than code. Version banners: pin the exact library build.

Finds: cryptography inside vendor appliances with no source at all. Every signature was verified by recomputing the table from its defining formula and confirming the match against a real OpenSSL build.

certs.py · 323 lines

4 · Certificates and keys

Parses X.509 in PEM and DER, keystores, and bare private keys. Each certificate carries two algorithms — the subject key and the algorithm that signed it — plus an explicit expiry, which makes its exposure directly datable.

Finds: SHA-1 and MD5 signatures, RSA under 2048 bits, expired certificates, and long-dated ones. It also resolves post-quantum certificates from their OIDs even when the underlying library cannot parse the key type.

configs.py · 157 lines

5 · Configuration

Reads nginx, Apache, sshd, openssl.cnf and Java security policy for cipher lists, protocol lists and key-exchange groups. Deliberately ignores disable-lists, since those are evidence of good hygiene rather than of weak cryptography in use.

Finds: the cheapest wins in any migration — usually one line and a service reload.

network.py · 283 lines

6 · Live network

Actually connects. Determines which TLS versions an endpoint accepts, which cipher it picks, what certificate it presents, and — the important part — whether it can negotiate a hybrid post-quantum key exchange.

Finds: ground truth. Source says what was written, config says what was intended, only the wire says what is negotiated. TLS 1.3 over a classical group is still Shor-broken, and the version alone never tells you that.

A detail worth knowing, because it is a good answer

The network sensor has three possible verdicts, not two: supports hybrid PQC, does not support it, or could not be tested. Python's TLS library cannot offer these groups, so the tool drives an OpenSSL 3.5+ command-line binary instead — and if neither is available it says "not determined" rather than reporting an absence of support it never actually tested.

07

How risk is scored

Two ideas, both in app/engine/risk.py.

Mosca's inequality

Three numbers. X is how long the data must stay secret. Y is how long migration takes. Z is years until a quantum computer exists.

if X + Y > Z:   the data you seal today is readable by someone recording it now
exposure     =  X + Y − Z      # in years

X comes from the data sensitivity setting — restricted 25 years, confidential 10, internal 5, public 1. Y comes from where the finding was found: a config line is half a year to change, a source call site two years, a binary with no source four. Z comes from the Q-Day slider.

The part that impresses cryptographers

Z is genuinely unknowable, so the tool does not assert it. It is modelled as a triangular distribution over (earliest, likely, latest), and the tool runs a Monte Carlo to report the probability of exposure alongside the exposure at the median. Any tool that hardcodes a Q-Day is bluffing, and saying that out loud is worth more than any feature.

The score itself

Deliberately a transparent product of named factors rather than a fitted model, because a judge who can audit the arithmetic will trust the output. Every term below is visible in the evidence drawer beside its input value.

FactorWhat it does
base_by_classStarting point from the quantum class — 50 for Shor-broken, 30 weakened, 26 unresolved, 12 hybrid, 6 safe. Raised to at least 50 if the algorithm is already disallowed classically, because MD5 is broken today, not in 2034.
algorithm_risk_adjustPer-algorithm correction where a class is right but severity is not uniform inside it. TLS 1.3 is technically Shor-broken but plainly less urgent than TLS 1.0, so it carries 0.45.
business_criticalityWhere the evidence lives. Production 1.0, vendored 0.75, test fixtures 0.4 — inventoried, but never leading the queue.
exposure_multiplierInternet-facing assets are recorded by anyone on the path, so network findings weigh more than dependency findings.
mosca_termThe exposure gap, contributing sub-linearly — ten years exposed is worse than five, but not twice as bad, because both already mean you have lost.
occurrence_termBlast radius. An algorithm reached from 200 call sites is a bigger migration than the same algorithm used once.
confidence_termDamps the score, so an uncertain finding can never outrank a certain one.

Severity bands are simply: critical at 70 and above, high at 45, medium at 25, low below that.

08

How advice is chosen

The problem statement asks for alternatives selected "based on risk profile, latency, cost". That is a constrained choice, not a lookup, and the constraint that dominates is size.

ReplaceWithPublic keySignature / ciphertext
RSA / ECDH key exchangeX25519MLKEM768 (hybrid)1,216 B1,120 B
ECDSA P-256 signingML-DSA-651,952 B3,309 B
Firmware signingSLH-DSA-128s32 B7,856 B
AES-128AES-256—no change
The number to remember

An ECDSA signature is 64 bytes. ML-DSA-65 is 3,309. That is fifty times larger, and it breaks fixed-size protocol fields, database columns and constrained radio links. This is why post-quantum migration is an engineering problem rather than a mathematics one, and why the tool reports the size delta with every recommendation.

The deployment profile dropdown changes the answer:

ProfileEffect
generalHybrid key exchange, ML-DSA-65 signatures. The sensible default.
high-assuranceCategory 5 parameter sets — ML-KEM-1024, ML-DSA-87 — for long-confidentiality material.
constrainedSmallest parameter sets, and it will tell you plainly when no drop-in replacement fits and the device needs a hardware refresh.
long-livedSLH-DSA. Hash-based security is the most conservative assumption available, which is right when a signature must outlive the algorithm's peer review.

Every recommendation also carries a crypto-agility note. The highest-value advice for a hardcoded call site is usually not "swap to ML-KEM" but "extract a provider interface so the next transition is a configuration change" — which is the lesson the whole industry learned the hard way.

The CBOM output

The problem statement says "in standardised formats". There is exactly one standard: CycloneDX 1.6, published as ECMA-424, whose CBOM support originated at IBM Research. Emitted by app/cbom.py.

// one cryptographic-asset component, as the tool emits it
{
  "type": "cryptographic-asset",
  "bom-ref": "crypto/algorithm/rsa-2048/1f4c…",
  "name": "RSA-2048",
  "cryptoProperties": {
    "assetType": "algorithm",
    "algorithmProperties": {
      "primitive": "pke",
      "parameterSetIdentifier": "2048",
      "classicalSecurityLevel": 112,
      "nistQuantumSecurityLevel": 0
    },
    "oid": "1.2.840.113549.1.1.1"
  },
  "evidence": {
    "identity":    [{ "confidence": 0.94, "methods": [...] }],
    "occurrences": [{ "location": "crypto/rsa/rsa_lib.c", "line": 88 }]
  }
}

The Validate button checks required fields, enum membership, bom-ref uniqueness and confidence ranges, then reports PASS with the component count. It is a structural conformance check rather than full JSON-Schema validation, and the tool says so in its own output rather than overclaiming.

There is a second deliverable: the executive report (app/report.py), a self-contained HTML page with exposure, the migration programme grouped by target algorithm, and a stated limitations section. The CBOM is for compliance systems; the report is for the person who signs the budget.

Stack, and why each choice

LayerChoiceWhy this and not the obvious alternative
LanguagePython 3.14The certificate, TLS and binary-parsing libraries are all first-class here, and no build step means nothing to break at 3am.
Web frameworkFastAPI + uvicornTyped request models for free, and async-capable so a long scan never blocks the interface.
StorageSQLiteA single file, no server, no setup. Postgres would need a running service the demo could lose.
Front endVanilla JSDeliberate. No npm, no bundler, no build. React would add a toolchain that can fail on the morning for a UI this size.
ChartsHand-built CSSThe bar charts are divs. A charting library would be a dependency, and would break the air-gap guarantee if loaded from a CDN.
X.509cryptographyThe one place where writing it myself would be genuinely wrong.
Source parsingast + regexPython's own parser for Python; curated pattern rules elsewhere. tree-sitter would be more precise but is a multi-hour install risk — see the limitations section, we say this openly.
Binary parsingstruct, pure PythonAvoids LIEF and YARA as dependencies. Cryptographic constants are just byte arrays; you do not need a framework to find them.
The rule behind all of it

Three runtime dependencies, zero outbound calls. Every asset the interface loads is served from the same machine. That is checked automatically by the preflight, because the air-gap claim is the product's main advantage and a single CDN font would destroy it.

12

Backend

The one data structure that matters

Everything in the system is a Finding (app/models.py). A Finding is one cryptographic artefact plus every place it was observed:

Finding
  algorithm      # key into the registry, e.g. "rsa-2048"
  asset_type     # algorithm | certificate | protocol | key material | library
  scanner        # which sensor produced it
  evidence[]     # Evidence: location, line, symbol, snippet, technique, confidence
  key_size, mode, padding
  quantum_class  # filled in by the risk engine
  risk_score, exposure_years, confidence
  recommendation # filled in by the recommender
  extra{}        # mosca breakdown, scoring factors, path breakdown

Sensors produce them, the normaliser merges them, the risk engine scores them, the recommender annotates them, and the CBOM emitter serialises them. Nothing else is passed between stages.

One optimisation worth being able to explain

The Q-Day endpoint originally returned every finding with its full evidence — 516 KB on every tick of the slider, which made it take up to 1.8 seconds and feel broken. It now returns only what changed: the scores and their Mosca terms, and the browser merges them into the findings it already holds. 35 ms, 40 KB. It also only writes to the database when you release the slider, not while you drag.

13

Frontend

Three files, no build step, no framework, no dependencies: app/web/index.html, app.js (≈600 lines) and style.css. The server serves them as static files.

How it is organised

  • One state object. state holds the current scan id, findings, summary, Q-Day settings and sensitivity. Nothing else is stateful.
  • Render functions read state and rewrite the DOM. renderTiles, renderDistributions, renderMoscaFigure, renderTable. renderAll calls all four. There is no virtual DOM and none is needed at this size.
  • Filtering is client-side. The search box and the class and context dropdowns filter the findings already in memory, so they are instant and involve no request.
  • The drawer is built by DOM construction, not string concatenation, so a file path containing angle brackets cannot break the page.
  • Colours come from CSS custom properties, so the severity colour of a table row and of a chart bar are guaranteed to be the same value.

Why not React

A deliberate call, and a defensible one if asked. This interface has four screens and one interactive control. React would add npm, a bundler, a build step and a node_modules directory — every one of which is something that can fail on the morning of a presentation, in exchange for ergonomics this size of interface does not need. The same reasoning removed every charting library: the bars are styled divs.

15

Honest limitations

Say these before a judge finds them. Volunteering a limitation reads as rigour; being caught in one reads as overclaiming.

LimitationWhat to say
Non-Python source uses pattern rules"Python gets a real syntax tree. The other nine languages use a curated rule pack with per-rule confidence and comment stripping. Less precise, and that is exactly why every finding carries a confidence score. Full parsing is on the roadmap."
Symbol tables are ELF-only"For ELF we parse the section headers properly. Mach-O and PE fall back to scanning printable strings, which is reported as a different technique at reduced confidence — we do not claim we parsed a symbol table when we did not."
No measured accuracy"We have not measured precision and recall, and I will not invent a number. Building a hand-labelled benchmark corpus is the top roadmap item."
No container scanning"Not shipped. It is a roadmap item for the Grand Finale, along with the cryptographic asset graph."
No HSM or cloud KMS enumeration"Also roadmap. The honest position is that you can only enumerate at the boundary — key specs and mechanism lists — and pretending to see inside an HSM would be dishonest."
Test fixtures still appear"Deliberately. They are inventoried but weighted to 0.4 so they never lead the queue, and you can filter to production-only in one click."

How to change things

You want to…Do this
Rename the productChange PRODUCT_NAME in app/config.py. One line; it propagates to the console, the CBOM metadata and the reports.
Add a new algorithmAdd a _register(_a(...)) entry in app/knowledge/algorithms.py.
Add a detection ruleAdd a R(...) entry in app/knowledge/rules_source.py. Give it a realistic confidence.

Troubleshooting

SymptomFix
Console loads but is emptyNo scan in the database. Run run.py --demo-reset.
Scan spins foreverDo not wait on stage — the seeded scan is already there, click it and keep talking. Afterwards, check the terminal for a traceback.
"Address already in use"An old server is running. pkill -f run.py, then start again.
Certificate scanner finds nothingThe cryptography package is missing. ./.venv/bin/pip install cryptography.
Network sensor says "not determined"Expected without OpenSSL 3.5+. It is being honest, not failing. The demo does not depend on it.
Everything is broken and you have ten minutesrun.py --demo-reset, then run.py --preflight. If preflight is ALL CLEAR you are fine.
The two things you must never cut

If you run out of time on stage, drop the binary beat and the live-endpoint beat. Never drop the Q-Day slider or the CBOM validating as PASS — those two are what separate this from a list of grep results.
